## 协议与护栏修复（第三次试跑）

本批仅修复动作输入适配、供应商结束原因与日志、SQL 逻辑运算符误拒绝及提示。
不引入 DSL、工具继承体系或原生 function-calling 迁移；不降低 decision 的输出
上限，不扩大评测范围。沿用 minimal-diff 原则，将动作模型和解析集中到
`model_actions.py`，其余沿用现有调用链。

- DSML 支持直接工具参数、`args` 包装和旧轨迹实证出现的 `ToolAction` 包装。
  每步只接受一个完整调用，拒绝冲突、重复参数及未知工具；仍经过现有参数校验
  和 SQL 护栏。原始输出完整记录，缺少 thought 时只生成中性的调用说明。
- `length` 不再混同断流。决策可从截断响应恢复完整合法动作，不完整动作仍只
  允许原有的一次格式修复。最终回答保留部分文本，但轮次为 failed、错误为
  `OutputTruncated`，不当作成功答案或送评预测。模型调用本身记录
  `status=truncated`、`finish_reason=length`；摘要截断也不得提交。
- `model_calls.finish_reason` 采用幂等增量迁移，历史未知原因保留 NULL，
  不回填推断。正常 stop、缺少结束标记、其他结束原因及真实传输异常分别留证。
- SQLGlot 把 AND/OR 也归入 Func，现仅豁免这两个逻辑节点的函数名检查；
  子节点函数、表列白名单和只读边界仍检查。提示新增禁止 DSML、Markdown、
  额外说明和模拟工具结果的约束，兼容解析作为后备而非目标协议。

离线共 142 项测试通过；相关核心模块与 benchmark 适配源码的 Ruff、增量 mypy
通过。验证包括截断决策恢复、最终部分回答留档且唯一失败终态、摘要截断拒绝、
未知结束原因拒绝、工具参数与嵌套危险函数校验、旧表增量迁移。对第二次运行的
76 次原始决策响应只读回放，均能提取结构合法动作；这不是 76 次业务正确性证明。
检查不扫描外部官方缓存源码的类型问题，也未改动该缓存。

### 剩余问题与边界

1. **输出预算仍是主要阻塞。** 下一批应分阶段处理最终回答的预算与长度要求，
   先验证当前供应商配置，再做有界实验；不能仅把 length 改成 completed 来提高完成率。
   连续空决策的终态仍是通用 JSONDecodeError，后续可在保留原始结束原因的基础上
   改善面向用户的错误分类，避免排障误读。
2. **查询成功不代表答案 SQL 符合题意。** 6 个已完成但 EX 错误的查询含额外列，
   其中部分还返回了多余候选行。例如题 1472 用 LIMIT 5 回答“最少者”，题 1312
   在专业名称外还返回姓名和关联键。应区分探查查询与最终答案查询，不能修改官方
   评分器忽略列或只取第一行来刷分。
3. **还有一个方言映射缺口。** `INSTR` 经 SQLGlot 转成 `STR_POSITION` 后仍被
   函数白名单误拒绝（题 847）。本轮 AND/OR 误拒绝未再出现，但不能据此说护栏已
   覆盖所有函数别名。本轮另外两个工具错误分别是错误参数名和 GROUP_CONCAT
   单元格超过资源限制；后者应保留资源护栏，让 Agent 缩小探查，不直接放宽限制。

所有本次日志写入运行目录的 `sessions.db`：20 条轮次终态、20 个 done、138 次
模型调用、96 对工具调用与结果事件；包含实际输入、原始可见输出、结束原因、
usage、SQL 与结果。根目录 `sessions.db` 和 `business.db` 前后 SHA-256 相同，
旧两次运行未迁移或覆盖。评分器验证了数据库哈希未变。

本批修复及约定的单次 20 题复跑完成。4/20 已满足非零 EX 的最低门禁条件，
但不是产品正确性验收；500 题和业务九题真实模型回归均未执行。任何后续核心

### 第六轮两项改动

1. **语义层自动探测增强（`benchmark/bird_data.py`）。** 新增 `_column_profile`：
   数值列返回 `MIN/MAX` 范围，TEXT 列返回至多 3 个 `DISTINCT` 示例值（单值超 40
   字符的长文本跳过）；表描述追加真实行数；外键在引用列为空时标注“主键”，并对
   复合外键去重。此前 `yearmonth.Date` 仅有 `type=TEXT`，模型无法确认格式；增强后
   显示 `示例: '201112', '201201', '201202'`，YYYYMM 口径可直接判定。
2. **`answer_columns` 列数校验契约。** `AnswerAction` 新增必填 `answer_columns`，
   要求模型在作答前显式声明问题要求的答案列；`react_loop._answer_column_error`
   校验最终查询返回列（小写化）与声明完全一致，不通过则生成 `answer_guard` 错误
   事件并回到决策循环，由模型重写最终 SQL。该项修复了“额外列/辅助列”这一类
   确定性错误：1471、1312、717、531、195 等题由模型自行声明单列后纠正。

测试侧同步更新：`tests/test_react_loop.py` 的 `answer()` 辅助函数支持
`answer_columns`，`tests/test_bird.py` 以显式别名 `SUM(amount) AS total` 验证
契约（无别名表达式经护栏规范化后列名为 `_col_0`，故最终查询应显式加语义别名）。
当前 `pytest` 为 152 passed。

### 剩余 5 题的归因

第六轮错误题为 1149、1028、847、340、341，逐题核对预测 SQL、gold SQL 与模型
最终声明的 `answer_columns` 后，没有一项属于架构缺失或工程缺陷，均为模型对问题
语义与 gold 口径的判断差异：

- **1149（声明与问题意图脱节）。** 模型声明的 `answer_columns` 为
  `inpatient_male / outpatient_male / ratio_in_to_out` 三列，契约因此通过，但问题
  只要 “deviation in percentage”——应为 `*100` 的单列百分比。契约能校验
  “SQL 列 == 声明列”，无法校验“声明列 == 问题意图”，且百分比换算理解错误。
- **1028（并列语义）。** 已正确声明单列，但用 `HAVING COUNT(*) = (MAX 子查询)`
  返回所有并列最多的球队；gold 用 `ORDER BY COUNT DESC LIMIT 1` 取一个。
  “which away team won the most” 的单数语境默认取一个，模型过度展开并列。
- **847（过度工程与 NULL 处理）。** 已正确声明 `surname`，但自行把 Q2 时间字符串
  解析为分钟数排序并加 `NOT NULL` 过滤；gold 直接 `ORDER BY q2 ASC`（SQLite 中
  NULL 默认排最前）。模型的数值排序看似更严谨，却与 gold 的简单口径不一致。
- **340 / 341（返回 id 还是 name）。** 模型声明并返回人类可读的 `name`，gold 返回
  主键 `id`；341 还叠加逻辑范围差异——模型按德摩根写成“两个 ID 任一为空”，gold
  字面为 `cardKingdomId IS NULL OR cardKingdomId IS NULL`。

**结论。** 可被代码或契约确定性修复的错误（输出协议、截断、额外列、缺校验）已
基本清完，EX 随之从 0% 收敛到 75%。剩余 5 题都需要理解自然语言意图并贴合 gold 的
具体取舍（百分比换算、并列、排序与 NULL、id/name），不存在通用且不误伤的硬规则
可覆盖；这部分落在 deepseek-flash 指令遵循与语义判断的能力边界，同时叠加 BIRD
gold 自身反直觉或不严谨的写法（直接文本排序、返回 id、重复条件）。

若继续做边际提升，应限定为 prompt 层的口径偏好并逐题验证，而非架构改动：百分比
`*100` 且单列、最高级单数语境默认 `LIMIT 1`、排序直接用原列不自行解析时间也不加
`NOT NULL`、评测默认返回主键 id。上述偏好不保证收益，且可能在其他题上适得其反。
