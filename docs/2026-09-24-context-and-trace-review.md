## 1. 结论与证据边界

工具执行链已有明显改善：商品销量查询能够逐步获取必要信息后成功执行；月度查询能够在一次方言错误后直接修正。主要断点已转移到查询依据向回答阶段的传递，以及跨轮证据选择。

投影层值得保留。存储与模型视图分离、纯函数投影、消息分类的方向合理，但当前实现仍较依赖固定条数和字符串前缀限制。它尚未形成完整的、保留查询依据的上下文管理机制，也没有足够实验支持将其称为已验证的创新。

本次证据范围：

- 11 次用户输入、9 条助手回答、20 次工具调用。其中元数据工具 13 次，SQL 执行 7 次；SQL 成功 6 次，方言错误 1 次。
- 包含一次问候、两次没有结束记录的重复提问，没有原测试中的“可以”轮，峰值月问题也增加了“刚才 Q4”的表述。因此不是严格相同的九题回归，不能直接记为 9/9 通过。
- 使用当前护栏重建查询，并固定相对日期为 2026-09-24，只读重算业务数据后，6 条成功 SQL 的结果均与日志一致。这是复核重建，不是历史实际执行 SQL 的完整留档。
- `thought` 文本没有落库。可以评估工具行为的连贯性，不能逐步核对模型当时展示的决策说明，更不能据此还原模型内部推理。
- 本组轨迹没有摘要记录，没有触发压缩。工具文本和回答未触及现有字符上限，月度结果 19 行也未触及工具前 20 行限制。

## 3. 问题清单

### P1：查询依据在回答阶段丢失

**状态：轨迹已证实。【L25 已修复】**

事件 16 的 SQL 明确筛选 `2026-01-01 ≤ ordered_at < 2027-01-01`，事件 17 却回答"没有时间字段，无法确认是否为今年"。事件 42 明确使用 `COUNT(DISTINCT customer_id)`，事件 43 又称去重规则没有说明。

`react_loop.py` 只把本轮最后一条事实性工具返回交给 `chat_stream_final()`，没有传入本轮 SQL 参数、指标口径及其他相关结果。工具名与参数虽在 `main.py` 中写入数据库，却没有进入本轮回答输入。决策调用生成的 `final` 内容也被丢弃，随后重新调用模型生成回答。

**建议：**回答阶段接收本轮全部相关查询依据，至少包含口径、SQL、时间条件、执行状态和结果。若保留独立的回答调用，决策阶段只决定是否结束及使用哪些证据，避免生成一份随后丢弃的完整答案。

**L25 修复（2026-09-25）：**
- 引入 `ToolResult` dataclass（tools.py），execute_sql 返回结构化结果（sql/columns/row_count/truncated）
- `react_loop.py` 收集本轮所有成功 execute_sql 的 `(sql, result)` 作为 `sql_evidence`
- `chat_stream_final()` 新增 `sql_evidence` 参数，优先于单条 tool_output 传递给回答模型
- 验证：Q1"今年各门店销售额"回答明确标注"今年（2026-01-01 至 2026-12-31）"，不再说"无法确认"

### P1：日志不足以解释一次完整执行

**状态：轨迹与代码均证实。【L26 部分修复】**

当前已保存工具名、参数、返回值，较旧版有进步，但仍缺少：实际模型请求、原始动作响应、简短决策说明、模型配置、usage、耗时、工具调用标识及明确轮次终态。成功查询只保存模型提交的 SQL，没有保存护栏改写后实际执行的 SQL。

事件 18 只有用户提问；事件 19–20 停在获取口径。现有日志无法区分用户取消、连接中断、执行异常或其他原因。

**建议：**记录请求与动作、实际执行 SQL、结构化工具状态、最终或部分回答，以及 `completed/failed/cancelled` 终态。决策说明应简短、可审计，不要求记录或还原内部思维链。日志不得包含 API 密钥。

**L26 修复（2026-09-25）：**
- 统一调用入口：tool_result 事件携带 `invocation`（编号）、`elapsed_ms`（耗时）、`is_error`、`error_type`、`sql`（护栏改写后实际执行 SQL）
- 实际执行 SQL 落库：header 格式 `[execute_sql(args) → SQL: 实际执行SQL]`，区分模型提交与实际执行
- 轮次终态：流结束时发 `done` 事件（`status=completed/max_iters/failed` + `invocations`），控制台打印 `[轮次结束]` 日志
- 控制台可观测性：`[工具#2 execute_sql 15ms] SELECT ...` 格式日志
- **仍未修复**：实际模型请求/原始动作响应/usage 落库（留 L27+）

### P1：工具结果在进入日志前已丢失部分数据

**状态：代码风险，本组结果未触发。**

`db.execute_query()` 先获取查询返回的全部行，再只将前 20 行格式化为工具返回。后续日志保存的也是这段文本，剩余行没有完整留档。因此投影层的“完整内容存于日志”提示，不能保证恢复完整查询结果。

`Total rows` 是 SQL 返回的行数，可能已受 `LIMIT` 限制，不是全部匹配行数。

**建议：**区分查询返回结果、模型可见预览和界面展示；保存有明确上限的查询结果及截断状态，模型按完整行读取预览，并可通过结果编号恢复其他部分。超过执行上限的数据需要分页或重新查询，不能宣称已完整保存。

### P1：历史事实选择缺乏相关性与有效性判断

**状态：轨迹已证实。【L26 部分修复】**

历史仅保留全局最后四条事实性结果。已解决的 `DATE_TRUNC` 错误仍占据一个名额，早先成功的 90 天结果 23 被挤出，事件 45 因而重新查询。该次重查恢复了可靠依据，不能简单归为无效重复。

最终运营总结时，商品销量原始结果 31 也不在所保留的工具事实中，部分数字依赖历史助手回答。

**建议：**优先保留追问相关的成功结果；已解决错误退出后续业务上下文。保留精简结果索引，允许 Agent 按编号读取旧结果，避免只能依赖助手复述或重新执行 SQL。

**L26 修复（2026-09-25）：**
- 新增 `KIND_ERROR` 分类：工具执行失败（SQL 错误/护栏拒绝/异常）落库时标记为 `kind=error`
- 投影层自动过滤：`project_history` / `find_compressible` / `_budget_split` 只选 `kind=result`，错误结果不再占据历史事实名额
- 验证：构造含 kind=error 的历史，投影中 tool 消息数正确排除错误结果
- **仍未修复**：成功结果的相关性选择（当前仍为全局最后 N 条）、结果索引/按编号读取（留 L27+）

### P2：预算统计与实际模型输入不一致

**状态：代码问题，本组未导致压缩。**

`_round_cost()` 按每轮最后四条事实计费，`project_history()` 最终却只发送全局最后四条。当前轮问题、工具链和包装文本也未统一纳入压缩判定。`/usage` 显示的是重新计算的历史投影加系统提示，而非最近一次实际请求。

`estimate_tokens()` 是启发式估算，不能视为供应商实际 token 用量。代码中的 700k 水位与固定条数、字符限制并存：即使离水位很远，局部规则仍会删除内容。

**建议：**先确定将要发送的内容，再统一计量。分别记录估算输入成本和供应商实际 usage；模型窗口配置、应用期望成本与输出预留应明确区分。

### P2：压缩缺少验证，来源顺序与范围不严谨

**状态：代码风险，本组未触发，不能宣称已验证通过。**

摘要非空就会被截到 800 字并替换历史，没有验证数字、引用、来源版本或替换收益。压缩输入依次拼接旧对话、工具结果和旧摘要，不保证逻辑时间顺序。`replaces_range` 只记录首尾 ID，无法准确表达非连续来源，旧摘要参与时还可能产生误导性范围。

“句子边界截断”只能减少残句，不能证明事实保真。保留所有具体数字与固定 800 字上限之间也可能存在不可满足的冲突。

**建议：**保存精确来源集合及逻辑位置；验证摘要结构、事实引用和替换收益后再提交。超长或不合格摘要应拒绝提交，不应通过继续切字符串把它变成合格摘要。

### P1：轮次、取消与并发缺少完整保护

**状态：中断记录已观察到；并发后果属于代码风险。【L26 部分修复】**

当前锁只保护压缩，不保护同会话请求。轮次分配、消息写入和后台压缩可能交错。流式回答没有覆盖异常与取消的可靠收尾，部分文本和结束原因可能无法保存。

另外，`session_store.init_db()` 每次启动都会重写所有历史 `turn`，并非仅回填缺失值。其算法在会话 ID 改变时重置计数，多会话消息交错时可能破坏原有轮次编号。

**建议：**同会话执行串行化，所有退出路径记录终态；历史回填作为受控迁移，只处理确需迁移的数据。上述问题涉及日志完整性，不属于本轮暂缓的 SQLite 性能优化。

**L26 修复（2026-09-25）：**
- 轮次终态事件：`done` 事件携带 `status=completed/max_iters/failed`，所有退出路径（正常结束/最大步数/解析异常）均发 done
- 控制台终态日志：`[轮次结束] status=completed invocations=5 session=...`
- **仍未修复**：用户取消（SSE 断开）的可靠收尾、同会话请求串行化、init_db 重写 turn 问题（留 L27+）

### P2：语义元数据与执行约束仍不一致

**状态：方言错误与元数据缺口已观察到，执行越界属于代码风险。**

商品销量已补充关联表依赖，但 `time_field` 仍为空，口径工具返回“时间字段：无”，需要模型自行从订单 schema 推断时间关联。数据库是 SQLite，而模型仍生成了 `DATE_TRUNC` 等其他方言语法。

隐藏表限制主要位于元数据工具，SQL 护栏没有对应的表级访问校验；已有 `LIMIT` 也不会被强制限制到最大允许值。

**建议：**补齐跨表时间口径，明确目标方言；让元数据可见性与执行访问范围一致，并校验已有 LIMIT。以上均可在保留模型自由生成 SQL 的前提下实施。

## 4. 投影层是否值得存在，是否有创新

### 存在价值

值得保留。完整轨迹用于审计与恢复，模型输入则需要围绕当前任务选择内容。将两者分离，有利于控制输入成本、减少无关信息，并为复现与策略评估提供明确边界。

当前合理的部分是存储与视图分离、纯函数投影，以及元数据、查询结果和对话的分类。细粒度工具也已在本次轨迹中体现价值。

需要改进的是选择单位：从“消息和字符串前缀”转向“完整查询依据”。一个可用的依据单元可以包含：用户需求、使用的口径与时间范围、SQL、执行状态、结果或结果引用。

这属于结构化工具回执，不等于 NL2DSL2SQL。模型仍自主决定工具调用并生成 SQL；投影层负责保持行动、条件和结果之间的联系。

### 创新判断

当前实现有工程价值，但没有足够证据称为已验证的创新点。更值得研究的是面向 NL2SQL 的证据保留策略：在相同输入预算下，优先保留与追问相关的查询依据、用户修正的口径和可恢复的结果引用。

可以在固定数据与问题集上比较“最近 N 条”与“相关证据选择”两种策略，考察追问正确率、重复查询次数、输入成本和压缩后的事实保留情况。需要通过对照实验说明收益，而非仅凭模块拆分或命名主张创新。

## 5. 是否过度依赖硬截断

是。问题主要在于多个固定限制叠加，而且缺少统一的恢复路径。

| 限制 | 当前影响 |
| --- | --- |
| 工具返回只展示前 20 行 | 部分查询结果在进入日志前丢失 |
| 结果 2000 字、元数据 1500 字 | 不区分字段、关系和修复信息的重要性 |
| 历史只留四条事实 | 即使预算充足，也会淘汰相关旧证据 |
| 本轮只看最近八条工具返回 | 长任务可能失去早期必要信息 |
| 对话 4000 字、摘要 800 字 | 末尾修正、约束和事实可能被丢掉 |
| 回答只使用本轮最后一个结果 | 固定数量的信息丢弃，多结果任务容易失真 |

`truncate_sentence()` 接受逗号作为边界，找不到边界时仍直接切字符。它无法保证 JSON、SQL、schema 或数字表格的结构和语义完整。

但本组轨迹没有触及字符和行数截断上限。实际影响明确的是四条历史事实限制，以及回答阶段丢失 SQL 和口径。因此，不能把本轮所有问题归因于超长文本裁剪。

建议保留执行行数、输入预算等硬上限，将任意字符串前缀截断降为最后的保护措施。正常路径应按完整对象选择：必要口径完整保留，结果按完整行展示，长结果提供引用或分页，已解决错误退出业务上下文，不合格摘要不提交。

## 6. 工具契约设计的参考价值
```python
@dataclass
class ToolResult:
    content: str
    is_error: bool = False
# "runtime_error" | "timeout" | "schema_error"
    error_type: str | None = None
# 成功后是否应立即结束本轮 Agent 运行
    stop_after_success: bool = False
class BaseTool(ABC):
    name: str
    description: str
    input_schema: dict[str, object]
    params_model: ClassVar[type[BaseModel] | None] = None
# 执行工具调用，返回结果或错误
    @abstractmethod
async def invoke(self, params: dict[str, object]) -> ToolResult: ...
```

用户提供的 `ToolResult` / `BaseTool` 示例值得借鉴，重点是统一结果、参数校验和调用边界，而不是引入继承体系。此处仅评估示例的设计，不认定它就是 Claude Code 的实际内部实现。

当前 `tools.py` 将成功结果、空结果、安全护栏拒绝和数据库错误都表示为字符串，`react_loop.py` 主要按工具名称分类。这使 SQL 错误也可能占据历史事实名额。结构化工具契约能够直接改善这个问题，且不改变模型自主选择工具、生成 SQL 的产品定位。

### 哪些设计值得采用

| 示例设计 | 当前项目的建议 |
| --- | --- |
| `ToolResult` | 采用统一结果类型，让执行器、日志和投影明确识别成功与失败，而非解析字符串中的错误标记 |
| `error_type` | 区分参数校验失败、SQL 安全拒绝、数据库执行失败和超时；参数 schema 与数据库 schema 错误不能混为一谈。错误类型用于反馈和有限恢复，不意味着自动重试 |
| `params_model` | 执行前实际校验参数，并由 Pydantic 模型生成 `input_schema`；工具说明也从统一注册信息生成，避免多份定义漂移 |
| `BaseTool(ABC)` | 暂非必需；当前无状态函数加轻量注册表、统一调用入口即可，出现真实的状态或生命周期需求后再考虑类体系 |
| `async invoke` | 按实际 I/O 实现决定；把同步 SQLAlchemy 查询放进 `async` 函数不会自动变成非阻塞，协程超时也不等于底层数据库查询已停止 |
| `stop_after_success` | 当前普通查询工具不建议采用；一次 SQL 成功不代表合计、占比、对比等整项任务已经完成 |

`is_error` 与 `error_type` 必须保持一致，可由错误信息推导状态或统一校验，避免出现“成功但携带错误类型”的矛盾。普通 `dataclass` 的类型注解本身不提供运行时校验。

### 结果不能只有 `content: str`

查询工具除可读文本外，还应保留结构化执行依据：实际执行 SQL、绑定参数（如有）、列与行、截断状态，以及需要跨轮恢复时的结果引用。已取得的指标口径、时间条件应与调用链关联；不能假设 SQL 执行工具能自行识别业务口径，也不能为尚未跟踪的信息补造元数据。

成功但没有匹配行、成功但结果不完整、执行失败是三个不同情形。前两者不应被当作错误；截断结果也不能直接作为全量合计或占比的依据。

第 3 节中“查过却无法确认时间范围或去重口径”的问题，需要传递这些依据才能解决。仅把原字符串包进 `ToolResult.content`，不会修复证据丢失。

### 与投影、日志和执行器的分工

工具返回执行上限内保留的结构化结果并标明完整性；日志保存调用事实及结果；`context.py` 根据当前任务选择字段、完整行和结果引用，生成模型可见视图。展示时的裁剪不应反向破坏留档数据。工具契约提供结构，不能代替执行行数上限、统一上下文预算或结果恢复能力。

统一调用入口负责调用编号、参数校验、耗时、错误映射及结果记录，先记录结果再发布事件。会话编号与轮次终态属于编排层，不必全部塞入 `ToolResult`。已解决错误可以退出业务投影，但原始错误事件仍须留档。

普通工具只报告执行结果；模型决定继续调用还是回答，执行器负责预算、取消和终态。若未来确有直接返回并结束的专用工具，再增加受执行器约束的终止策略，不应让普通查询的成功状态直接结束整轮任务。

**落地范围：**先采用统一结果类型、参数校验和统一调用入口，再让投影与回答消费结构化依据。保留现有细粒度工具和模型生成 SQL，不引入查询 DSL、插件体系或不必要的工具继承框架。这是工程契约改进，不单独构成已验证的创新点。
